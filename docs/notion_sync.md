# Notion syncing is central command's job

**Policy, set by Emma 2026-07-31: central command runs the syncing.** This repo's work loop
does not create, edit, or push Notion pages.

An earlier version of this file said the opposite — that the repo was the source of truth,
that Notion was a one-way copy, and that nothing should be authored in Notion. That was my
call, not Emma's, and it was wrong on both counts: she had asked for **bidirectional**
editing and for **central command to own the integration**, since it already knows how.
Two pages were created directly from this repo before that was corrected. Central command
owns them now and may keep, replace or delete them.

## What this repo does provide

`wikibase/analysis/cycles_review.md` — all 35 tangles, one section per tangle, every member
with its ancestor count, descendant count, depth, and whether it reaches `Q1` Aster.
Generated by `wiki-scripts/build_cycles_notion.py`; regenerate after any change to
`wikibase/items/`. It is a plain Markdown file with no Notion coupling.

The column that matters is **`ancestors`** — distinct records reachable upward. See
`cycle_policy.md`: load-bearing means the ancestry reached *through* a node. `descendants`
is context only, and `qa_cycles_load.tsv` ranks by it and is wrong to.

Every section ends `Decision: not made — needs Emma`. The generator reports what the data
shows and proposes nothing.

## One correction worth carrying over

**35 tangles is not 71 cycles.** A tangle is a strongly connected component and can contain
many distinct loops. The "71 cycles" figure in `GENEALOGY_QA.md` and the 71 rows of
`qa_cycles_proposed.tsv` counted loops, using an enumerator that was never deterministic —
three runs over one unchanged `edges.tsv` returned 45, 50 and 46. Anything presenting a
tangle count should say "tangles", not "cycles"; the page built on 2026-07-31 did not, and
that is what made the two numbers look contradictory.
