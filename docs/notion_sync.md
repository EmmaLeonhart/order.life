# What is synced to Notion, and what is not

**Written 2026-07-31.** Emma asked for the genealogy review to live on a surface she can
read and decide from, instead of arriving as decisions already taken in commit messages.

## The rule

**The repo is the source of truth. Notion is a copy.** Every synced page is generated from
a Markdown file under `wikibase/analysis/`, and that file is generated from the dump. If
the two ever disagree, the repo wins and the page gets regenerated — never the other way
round. Nothing is authored directly in Notion.

## What is synced

| Notion page | generated from | generated by |
|---|---|---|
| [Ancestry cycles — every one, with ancestor counts](https://app.notion.com/p/3ae96556906781e98643c34a75bd8a86) | `wikibase/analysis/cycles_review.md` | `wiki-scripts/build_cycles_notion.py` |
| [order.life — Work Loop](https://app.notion.com/p/3ae96556906781699fbafe5eb90e89c6) | hand-written summary; the merges and the current state | the work loop, each tick |

The cycles page is the important one. It has **one section per cycle**, and in each section
a table of every record caught in it with:

- **`ancestors`** — distinct records reachable upward. **This is the only column that ranks
  anything.** `cycle_policy.md` and `queue.md` both say load-bearing means the ancestry
  reached *through* a node. A repair that collapses this number is severing a gateway.
- `descendants` — context only. Deliberately ranks nothing. `qa_cycles_load.tsv` ranks by
  descendants lost and is wrong to.
- `depth` — longest chain upward, computed over the cycle-condensed graph so it stays well
  defined despite the cycles.
- `→Aster` — whether `Q1` Aster is reachable upward at all.

Each section ends with **`Decision: not made — needs Emma`**. The generator states what the
data shows — shared Wikidata ids, shared labels, records with more than two parents,
edges Wikidata contradicts, recorded birth years — and proposes nothing.

## What is NOT synced

`queue.md`, `devlog.md` and `todo.md` stay in the repo. The cockpit renders those directly
(see the Topaz section of `CLAUDE.md`); copying them into Notion would give them two homes
and no owner.

## Regenerating

```
python wiki-scripts/extract_genealogy.py      # refresh the graph  (~13 min)
python wiki-scripts/dump_qa_errors.py         # refresh the tangles
python wiki-scripts/build_cycles_notion.py    # rewrite cycles_review.md
```

Then push `cycles_review.md` to the Notion page. Do it after **any** change to
`wikibase/items/` — the counts move as soon as the dump does.

## Why this exists

Repairs were being applied one at a time, each justified in a commit message, with the
reasoning spread across tool docstrings and devlog entries. That left Emma auditing
decisions after the fact rather than making them, and it hid how much a repair cost: a
single edge cut on 2026-07-31 stripped ancestry from **27,569 records** while every gate in
the repo reported a clean win, because every gate measured width and none measured depth.
It was reverted. `wiki-scripts/compare_depth.py` is now the gate for that, and this page is
the surface that makes the same information visible before anything is applied.
